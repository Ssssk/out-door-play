# 总体架构规范

## 基线形态

默认采用前后端分离与后端模块化单体。只有出现独立伸缩、独立发布、组织边界或可靠性隔离的真实需求，并具备可观测性和运维能力时，才拆分微服务。

```text
uni-app Client
  -> HTTPS API /api/v1
NestJS HTTP Adapter
  -> Application Services
  -> Domain Model
  -> Ports
       -> Prisma / conditional Redis / conditional RabbitMQ Adapters
```

## 依赖方向

- 展示层依赖应用层；应用层编排用例；领域层表达业务规则；基础设施层实现端口。
- 领域层不得依赖 NestJS Controller、Prisma Client、Redis 或 RabbitMQ 客户端。
- 模块之间通过公开服务、领域事件或明确端口协作，禁止跨模块直接访问内部表或私有 Provider。
- 公共包只承载真正稳定的横切能力，禁止形成无边界的 `utils` 垃圾场。

## 一致性

- 单库单模块内优先使用本地 ACID 事务。
- 数据库提交与消息发布需要一致性时使用 Transactional Outbox；禁止先提交数据库再“尽力发送”关键消息。
- 跨模块流程使用可恢复状态和幂等补偿，不伪装为全局强事务。

## 架构变更

项目数据访问基线为 Prisma 7。新数据库、新 MQ、新缓存用途、ORM 变化、跨模块依赖、公共 API 破坏性变更必须在设计中提供备选方案、迁移策略和 ADR。

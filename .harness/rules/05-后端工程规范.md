# 后端工程规范：NestJS

## 模块结构

每个业务模块推荐：

```text
modules/cart/
  api/                  # controller, dto, presenter
  application/          # commands, queries, use cases
  domain/               # entities, value objects, policies, ports
  infrastructure/       # Prisma，以及经批准才存在的 Redis/RabbitMQ adapters
  cart.module.ts
```

- Controller 只处理协议适配、认证上下文、输入 DTO 和输出映射，不写业务规则。
- Application Service 管理用例和事务边界。
- Domain Service/Entity 表达核心规则，不依赖框架。
- Repository 接口归属领域或应用层，实现位于基础设施层。

## NestJS 基线

- 全局启用 ValidationPipe，并采用白名单、非白名单拒绝和必要的类型转换。
- 使用 ConfigModule 与启动时配置校验；环境变量缺失应快速失败。
- 使用全局异常过滤器、响应序列化和 request-id/trace-id。
- 认证使用 Guard，授权使用显式策略或权限装饰器；禁止在业务方法中复制权限判断。
- OpenAPI 由代码与契约共同校验，公开接口必须有稳定 DTO 和响应定义。

## 并发与可靠性

- 事务内只执行数据库工作；网络、缓存和 MQ 副作用放在事务外或 Outbox。
- 更新库存、余额、积分等竞争资源时明确使用乐观锁、悲观锁、条件更新或序列化策略。
- 所有后台任务必须可重试、可观测、可取消或具备超时。
- 禁止无限重试；重试应指数退避、抖动并有终止/死信策略。

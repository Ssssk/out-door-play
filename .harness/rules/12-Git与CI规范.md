# Git 与 CI 规范

## 分支与提交

- 每个 Change 使用独立分支或工作树，命名包含 Change ID 与简短名称。
- 提交必须小而完整，可构建、可评审；不得混入无关格式化或生成物。
- 提交信息说明类型、范围和意图；破坏性变化、迁移和回滚要求在 PR 中突出。
- 禁止重写共享分支历史或绕过受保护分支。

## Pull Request

PR 必须链接 Change，列出范围、非目标、风险、测试证据、截图、迁移、灰度和回滚方式。评审意见关闭时说明修复或不采纳理由。

## CI 顺序

1. 契约与格式校验。
2. 依赖锁与供应链检查。
3. Lint、类型检查、单元测试。
4. 前后端构建。
5. MySQL 与当前 Change 实际采用的 Redis/RabbitMQ 集成测试。
6. API/事件契约测试。
7. E2E 与部署前检查。

失败步骤不得通过重复重跑掩盖不稳定；识别 flaky 测试后登记负责人和修复期限。CI 使用最小权限、短期凭证和受保护环境。

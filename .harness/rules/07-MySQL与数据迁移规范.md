# MySQL 与数据迁移规范

## 存储基线

- 使用 InnoDB、`utf8mb4` 和项目统一排序规则；Schema 只由 Prisma Migration 管理，生产禁止 `db push` 或任何 ORM 自动同步替代版本化 migration。
- 表和列使用清晰业务命名；主键策略、时间字段、软删除和租户字段必须全项目一致。
- 金额使用 `DECIMAL` 或最小货币单位整数；禁止 `FLOAT/DOUBLE` 存储财务值。
- JSON 仅用于变化频繁且不参与核心关系约束的扩展结构；需要查询的字段应结构化或建立可解释索引。

## 索引与查询

- 索引来自真实查询、唯一性和排序需求；复合索引遵循最左前缀并在设计中列出目标 SQL。
- 避免 `SELECT *`、无界列表、循环查询和 N+1；分页大偏移时评估游标分页。
- 慢查询优化必须提供执行计划或等价证据，不能只凭猜测新增索引。
- 外键是否使用由项目规则决定，但领域引用、删除行为和孤儿数据处理必须明确。

## 事务

- 默认隔离级别必须在部署配置中显式确认；关键并发场景写明期望锁语义。
- 事务尽量短，不进行外部 HTTP、文件上传、MQ 等等待。
- 捕获死锁或瞬时冲突时，只对可安全重放的完整事务有限重试。

## 迁移

- Schema 变化只能通过版本化 migration；每个 migration 有升级、回滚或前向修复说明。
- 大表变更评估锁表、复制延迟、磁盘、执行时长和在线 DDL 能力。
- 删除/重命名采用 expand-migrate-contract：先兼容新增，再迁移数据，最后删除旧结构。
- 迁移脚本必须在接近生产的数据规模和版本上验证；备份不能替代回滚演练。

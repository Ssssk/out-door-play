# 影响分析

## 触发条件

- 新功能、Bugfix、重构、依赖升级、配置、数据或基础设施变更进入设计前。
- 修改公开 API、共享组件、公共模块、表结构、Redis Key 或事件 schema。
- 线上故障修复需要确认影响面和回归范围。

## 不适用场景

- 完全隔离且不改变行为的文档修正。
- 尚未形成稳定需求，无法判断拟议变化。
- 用“全量回归”代替实际影响识别。

## 前置 Gate

- 需求和 AC 已达到可评审状态。
- 已确认目标平台、业务边界和主要数据流。
- 对关键仓库事实具有只读访问能力。

## 必读上下文

1. 当前 Change 的请求、澄清、需求、AC 和状态。
2. 全部与拟改模块相关的 Rules 和 Wiki。
3. 相关代码的入口、调用方、测试、配置、迁移、定时任务和消费者。
4. `knowledge/` 中相同模块、症状、依赖和事故记录。

## 输入

- 已批准或待批准的 FR/NFR/AC。
- 当前架构、调用图、数据流和部署拓扑。
- 目标变更的初步边界及已知风险。

## 执行步骤

1. 从用户入口到最终数据/事件画出当前链路和目标链路。
2. 列出直接修改文件、模块和制品，再沿导入、调用、订阅与数据依赖扩展间接影响。
3. 前端检查页面、分包、组件、composable、Pinia、请求层、权限、主题和平台条件编译。
4. 后端检查 Controller、DTO、用例、领域规则、Repository、任务、消费者和外部适配器。
5. 契约检查 OpenAPI、错误码、事件、配置、环境变量和旧客户端/第三方调用方。
6. 数据检查表、索引、约束、事务、历史数据、报表、备份和数据修复。
7. Redis 检查 Key、TTL、序列化、热点、失效、预热和多版本兼容。
8. RabbitMQ 检查生产者、消费者、routing key、schema、重试、DLQ、重放和积压。
9. 横切检查认证授权、隐私、日志指标、告警、容量、部署顺序、灰度和回滚。
10. 对每项标明“有影响/无影响/未知”，附事实证据、风险、验证方法和 Owner。
11. 形成回归范围：直接用例、上下游、共享能力、历史缺陷与核心业务链路。
12. 更新 `04-impact-analysis.md`，将未知高风险项升级为设计阻塞项。

## 技术约束

- “无影响”也必须提供依据，例如无调用引用、契约未变化或隔离边界证明。
- 必须检查后台管理端、定时任务、脚本、数据分析、旧客户端和隐藏消费者。
- 依赖升级必须读取官方迁移说明并识别 breaking changes；不得只看编译结果。
- 数据和消息兼容至少考虑滚动发布期间新旧实例同时运行。
- 前端跨端影响必须按目标端分别判断，不用浏览器结论代替小程序/App。

## 产物

- `04-impact-analysis.md` 完整影响矩阵。
- 受影响模块、契约、数据、运行时、调用方和测试范围清单。
- 风险等级、验证方式、发布/回滚约束与未决问题。
- 引用的历史知识、事故和 Change ID。

## 验证与证据

- 使用代码搜索、依赖图、契约、配置、运行证据或 Owner 确认支持结论。
- 从 API、表、Key、事件分别反查生产者和消费者，防止只做正向分析。
- 每个 P0/P1 风险都有消除、缓解、转移或书面接受策略。
- 测试计划能覆盖影响矩阵中的每个“有影响”项。

## 停止与升级条件

- 找不到关键接口、数据或消息的 Owner。
- 无法确认旧客户端、外部调用方或历史数据规模。
- 发现实际范围显著超过需求契约。
- 发现不可逆数据修改、公开契约破坏或安全边界变化但尚无专门评审。

## 禁止事项

- 不用“应该没影响”“只改一行”作为结论。
- 不只列直接修改文件，不忽略运行时和数据依赖。
- 不因测试成本高而把有影响项标记为无影响。
- 不在分析阶段执行生产查询或写入。

## 完成定义

所有前端、后端、契约、数据、缓存、消息、安全、运维和兼容维度均有有据可查的结论；回归范围明确；未知高风险项已阻塞或有 Owner；设计人员可以据此完成方案。

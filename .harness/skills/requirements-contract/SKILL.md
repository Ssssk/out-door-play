# 需求契约编写

## 触发条件

- 请求和澄清记录已形成，准备进入需求评审。
- 现有需求出现范围、规则、验收或非功能要求变更。
- Bugfix 需要把正确行为和防回归条件契约化。

## 不适用场景

- 关键业务决定仍无 Owner 或无法确认。
- 只需要技术方案、API schema 或编码步骤。
- 用测试用例反推并擅自改变产品要求。

## 前置 Gate

- Change 状态至少为 `clarifying`。
- 请求目标、用户、范围和非目标已明确；阻塞性问题已关闭或获得书面风险接受。
- 已检索知识库并核对领域术语和历史规则。

## 必读上下文

1. `00-request.md`、`01-clarification.md`、`status.yaml`。
2. `wiki/01-系统上下文.md`、`wiki/04-领域模型.md`、`wiki/13-领域术语.md`。
3. 相关 API、数据、错误码、权限和消息 Wiki。
4. `rules/01-开发流程规范.md`、`rules/10-测试与质量门禁.md`。
5. 相关知识记录、事故与历史 Change。

## 输入

- 已确认的业务目标、角色、流程、规则、异常、边界和数据口径。
- 业务优先级、兼容要求、目标平台及质量目标。
- 可接受的人工验证项以及必须自动化的关键路径。

## 执行步骤

1. 建立术语表并复用 Wiki 正式名称，消除同义词和歧义。
2. 读取 `source-baseline.json`，把每个正式需求映射到来源 ID 与稳定锚点。
3. 把需求拆为最小可独立验证的能力，使用 `FR-<DOMAIN>-NNN`。
3. 对性能、可靠性、安全、兼容、可访问性和可观测性建立 `NFR-<QUALITY>-NNN`。
4. 为每条 FR/NFR 写来源、优先级、业务规则、前置条件和可观察结果。
5. 使用 `AC-<DOMAIN>-NNN` 编写 GIVEN/WHEN/THEN 验收标准。
6. 覆盖主流程、空状态、失败、边界、权限拒绝、重复提交、并发冲突和超时。
7. 明确金额单位与舍入、时间/时区、ID、枚举、分页、排序和数据保留口径。
8. 为 uni-app 标明目标端和平台差异；为 NestJS 标明外部调用方与兼容窗口。
9. 建立 FR/NFR 到 AC 的追踪，确保没有孤立需求或无来源验收项。
10. 更新 `02-requirements.md`、`03-acceptance-criteria.md`，准备需求 Gate 评审。

## 技术约束

- 需求只规定 what、why 和外部可观察结果，不提前锁定 Controller、表名、Redis Key 或队列名。
- 性能要写数据规模、并发、百分位、阈值和测量环境；不得只写“快速”。
- 可用性要写超时、错误率、恢复目标或降级行为；不得只写“稳定”。
- 权限使用角色、资源、动作和数据范围表达，不能只写“登录后可用”。
- 金额使用最小货币单位或明确 Decimal 规则；时间说明业务时区和存储口径。
- 对仍在使用的旧版 uni-app 客户端，必须包含兼容验收条件。

## 产物

- `02-requirements.md`：功能需求、非功能需求、规则、范围与非目标。
- `03-acceptance-criteria.md`：稳定 AC、场景、预期和验证类型。
- FR/NFR/AC 追踪关系以及来源、Owner 和优先级。
- 更新后的来源锚点 → FR/NFR/AC 追踪，确保 AI 没有添加无来源规则。

## 验证与证据

- 每条需求至少关联一个 AC，每个 AC 至少关联一个需求。
- 每条 FR/NFR 至少关联一个原始来源锚点；来源基线必须为 verified 或经批准的 not-applicable。
- 测试人员在不知道实现细节时也能判定每个 AC 通过或失败。
- 正常、异常、边界、权限、并发、兼容和非功能场景均已检查。
- “合理、尽快、智能、友好”等模糊词已量化或转为澄清项。

## 停止与升级条件

- 同一业务规则存在互相冲突的负责人结论。
- 数据口径、金额、时间、权限或兼容策略无法确定。
- 验收依赖尚未确认的第三方能力或法规解释。
- 新增要求超出已受理范围，需要回到 request-analysis。

## 禁止事项

- 不用页面元素、类名、数据库字段替代业务要求。
- 不把验收标准写成“开发完成”或“测试通过”。
- 不删除失败和边界场景以降低实现成本。
- 不自行把需求 Gate 标记为通过。

## 完成定义

需求与验收均有稳定 ID、双向可追踪、可独立判定；业务规则和非功能阈值明确；无未处理的阻塞歧义；产品和相关 Owner 已具备评审所需内容。

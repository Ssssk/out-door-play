# UI/UX 与可访问性验收

## 触发条件

- 新增或修改页面、组件、导航、交互、文案、主题或平台能力。
- 运营活动需要视觉稿、状态稿和多端适配。
- 前端缺陷涉及可用性、键盘、安全区、可访问性或视觉回归。

## 不适用场景

- 无界面影响的纯后端变更。
- 代替产品负责人做业务 UAT。
- 用静态设计稿证明真实客户端行为已经通过。

## 前置 Gate

- 需求、用户角色、目标平台、主流程、失败流程和文案 Owner 明确。
- 设计来源和版本进入 Change，重大偏差有批准人。
- 可访问性和平台限制已进入 AC 或 NFR。

## 必读上下文

1. 需求、AC、页面流程、组件设计、API/错误码和目标端矩阵。
2. 前端、测试、安全 Rules 与 Wot Design Uni 使用基线。
3. 现有主题 Token、公共组件、页面和历史 UI 缺陷。
4. `frontend/ui-ux-review.md` 与 `verification/accessibility-test.md`。

## 输入

- 原型/设计稿版本、页面清单、文案、交互和视觉 Token。
- H5、微信小程序、App 的设备、系统和最低版本。
- 用户任务、异常、权限、弱网和可访问性场景。

## 执行步骤

1. 将每个页面/组件拆成正常、加载、空、错误、无权限、禁用、成功和弱网状态。
2. 核对信息架构、返回路径、导航栈、分包和深链入口。
3. 优先映射 Wot Design Uni 组件，记录确需业务封装的语义和边界。
4. 核对颜色、字号、间距、圆角、图标、层级和暗色/主题 Token。
5. 检查表单标签、帮助、校验时机、错误恢复、键盘类型和输入法遮挡。
6. 检查触控区域、对比度、动态效果、焦点顺序、语义和屏幕阅读提示。
7. 检查安全区、刘海、底部栏、横竖屏、长文本和不同尺寸。
8. 检查重复提交、破坏性确认、弱网、超时、离线和页面卸载竞态。
9. 在每个目标端执行视觉与交互验证，保存版本、设备和证据。
10. 将偏差分类为缺陷、批准差异或设计变更；设计变更返回设计 Gate。
11. 更新 UI/UX 和 accessibility 文件并给出 Owner 结论。

## 技术约束

- 禁止复制 Wot 基础组件来绕开统一主题和行为。
- 颜色和间距使用集中 Token，不在页面散落同义魔法值。
- 业务关键状态不能只靠颜色表达；文本与控件必须保持可识别。
- H5 结果不代表小程序/App；平台 API 和原生插件使用真实目标端证据。
- 截图需绑定制品版本、平台、设备和场景，不能只提供理想状态。
- 可访问性偏差必须有 Owner、期限和风险接受，不以“主要用户不需要”直接跳过。

## 产物

- `frontend/ui-ux-review.md` 页面状态和设计偏差矩阵。
- `verification/accessibility-test.md` 及设备/平台证据。
- 视觉、交互、文案和目标端缺陷清单。
- UI/UX Owner 审批或明确拒绝结论。

## 验证与证据

- 每个页面状态都有设计或明确不适用理由。
- 每个目标端至少覆盖主路径和平台专属能力。
- 关键组件在窄屏、长文案、键盘和安全区下无裁切重叠。
- 可访问性验证能由其他执行者复现，证据绑定当前制品。

## 停止与升级条件

- 设计稿、文案、目标端或 UI Owner 不明确。
- 实现需要改变业务流程、API、权限或需求范围。
- 平台限制使已批准 AC 无法实现。
- 发现支付、隐私、误导性操作或严重可访问性风险。

## 禁止事项

- 不用开发者自评代替独立 UI/UX 结论。
- 不只验收成功页，忽略错误、空和弱网状态。
- 不擅自修改设计稿或隐藏服务端错误。
- 不把未执行真机验证标记为 passed。

## 完成定义

页面和组件状态完整，Wot/Token 一致，跨端、响应式、文案和可访问性均有真实证据；设计偏差已批准或修复；UI/UX 结果可进入 UAT。

# 全栈解决方案设计

## 触发条件

- 需求 Gate 已通过或具备明确的评审授权，准备进入技术设计。
- 既有设计因范围、风险、接口或数据策略改变需要修订。
- Bugfix、重构或升级涉及跨模块、数据或运行时行为。

## 不适用场景

- 需求关键歧义尚未关闭。
- 纯实现任务已有批准设计，不需要改变方案。
- 为未来假设提前引入微服务、新中间件或复杂抽象。

## 前置 Gate

- `02-requirements.md`、`03-acceptance-criteria.md` 完整且需求 Gate 已通过。
- `04-impact-analysis.md` 已覆盖直接和间接影响。
- P0/P1 未知项有 Owner，无法消除时必须停在设计 Gate。

## 必读上下文

1. 当前 Change 全部需求、AC、影响分析、状态和审批记录。
2. `rules/02-总体架构规范.md` 至 `rules/13-发布回滚与可观测性.md` 中相关规则。
3. 前后端、接口、领域、数据、Redis、消息、权限、错误码、部署和观测 Wiki。
4. 相似 Change、ADR、事故、模式、反模式和解决方案。
5. 当前代码与测试事实，不能仅依据 Wiki 推断实现。

## 输入

- 稳定的 FR/NFR/AC、影响矩阵和风险清单。
- 当前架构、容量、兼容窗口、发布约束和团队运维能力。
- 可选方案及必须遵循的外部契约。

## 执行步骤

1. 写明目标、非目标、约束和设计驱动因素，逐项引用需求 ID。
2. 描述当前流程和目标流程，画出用户、uni-app、NestJS、MySQL、Redis、RabbitMQ 的时序。
3. 划分前端页面、业务组件、composable、Pinia 和 API 层职责。
4. 设计完整 UI 状态、Wot Token、目标端、可访问性和产品 UAT 路径。
4. 划分 NestJS Module、Controller、Application、Domain、Infrastructure 边界及依赖方向。
5. 设计 HTTP API、错误码、认证授权、幂等、并发和版本兼容。
6. 设计实体、表、索引、约束、事务边界、迁移与历史数据处理。
7. 决定是否使用缓存；定义 Key、值、TTL、一致性、失效、穿透/击穿/雪崩防护。
8. 决定是否异步化；定义事件、Outbox、生产确认、消费幂等、重试、DLQ 和重放。
9. 设计失败、超时、部分成功、降级、补偿和用户可见错误行为。
11. 设计日志、trace、SLI/SLO、告警、业务对账、容量、备份恢复和 Incident 响应。
12. 设计部署顺序、功能开关、灰度指标、数据库兼容窗口和回滚路径。
12. 比较至少一个合理备选方案，记录取舍及形成 ADR 的必要性。
13. 更新 `05-design.md` 及 frontend、backend、contracts 子文档，建立到任务和测试的映射。

## 技术约束

- 默认模块化单体；只有独立伸缩、故障隔离、团队边界等证据充分时才提出微服务。
- Controller 不承载业务规则；Application 管理用例；Domain 不依赖 NestJS/TypeORM/Redis/RabbitMQ。
- 本地数据库事务中不得等待外部 HTTP、Redis 或 MQ；关键事件使用 Outbox。
- MySQL 为持久业务真相时，Redis 只能作为派生状态，必须设计失效和恢复。
- RabbitMQ 按至少一次投递设计，消费者必须幂等，不宣称 exactly-once。
- uni-app 平台能力集中隔离，写明各目标端的降级与验证方式。
- 公开契约、数据和事件需支持滚动发布期间新旧版本共存。

## 产物

- `05-design.md`：完整全栈设计、时序、失败与发布策略。
- `frontend/page-flow.md`、`frontend/component-design.md`。
- `frontend/ui-ux-review.md`、性能、UAT、安全供应链和 operations 文档的设计输入。
- `backend/domain-design.md`、必要时的 `backend/migration-plan.md`。
- `contracts/openapi.yaml`、`error-codes.yaml`、`events.yaml` 的设计输入。
- ADR 候选、未决问题、风险处置和任务拆分依据。

## 验证与证据

- 每条 FR/NFR/AC 均能定位到设计组件和验证方法。
- 对事务、并发、缓存、消息、权限、错误、观测、发布和回滚执行反向审查。
- 用至少一个失败时序验证部分成功、重复请求和重试不会破坏业务不变量。
- 方案与当前代码、基础设施能力和容量约束一致。

## 停止与升级条件

- 需要改变需求范围、外部契约或数据口径。
- 需要新基础设施、生产权限、不可逆迁移或显著新增成本。
- 无法给出缓存一致性、消息幂等、数据库恢复或客户端兼容策略。
- P0/P1 风险仍依赖未经确认的假设。

## 禁止事项

- 不用“参考现有实现”“后续优化”掩盖关键设计空白。
- 不把框架目录图当成业务设计全部内容。
- 不以 Redis 锁或 MQ 重试替代明确的业务不变量和幂等策略。
- 不在设计 Gate 通过前开始跨模块实现。

## 完成定义

方案覆盖前后端、契约、数据、缓存、消息、安全、测试、观测、发布和回滚；关键决策有依据；需求到设计可追踪；风险和未知项已处理；评审者可据此判定设计 Gate。

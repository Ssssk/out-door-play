# 需求受理与分析

## 触发条件

- 收到新功能、缺陷、重构、数据修复、运营活动、依赖升级或基础设施变更诉求。
- 用户给出的是解决方案或一句话需求，尚未明确业务问题、范围和验收结果。
- 已有 Change 的目标或边界发生实质变化，需要重新澄清。

## 不适用场景

- 已批准需求的纯编码任务；使用对应实现 Skill。
- 只修改错别字且不改变行为、接口、数据或安全边界的工作。
- 未经授权代替产品负责人决定业务规则、优先级或上线时间。

## 前置 Gate

- 不要求需求 Gate 已通过，但必须有可识别的请求来源和负责人。
- 若涉及生产事故，先按应急流程止损，再补充本契约；不得因写文档延误止损。
- 若请求要求生产写入、数据删除或外部发布，只能记录需求，不能直接执行。

## 必读上下文

1. `.harness/manifest.yaml`、`rules/00-治理与优先级.md`、`rules/01-开发流程规范.md`。
2. `wiki/00-技术基线.md`、`wiki/01-系统上下文.md`、`wiki/13-领域术语.md`。
3. 相关模块 Wiki、代码、接口及活动中的 Change。
4. 执行 `knowledge-retrieval`，按领域、症状、错误码、技术栈检索历史经验。

## 输入

- 原始诉求、来源、提出人、期望时间和业务背景。
- 可用的截图、日志、工单、监控、用户反馈或复现信息。
- 当前行为、期望行为和已知限制；缺失项必须显式标为未确认。

## 执行步骤

1. 判断类型：feature、bugfix、refactor、migration、hotfix、operation-campaign、dependency 或 infrastructure。
2. 用一句可观察的业务结果重述问题，区分问题、目标和用户提出的实现建议。
3. 在 `changes/` 中检索重复、相邻或冲突 Change；记录复用、合并或依赖关系。
4. 执行 `requirement-baseline`，捕获原始 PRD/工单/截图/口述来源、版本、哈希和权限边界。
5. 核验当前事实：页面、API、模块、表、缓存、消息、权限、配置和发布拓扑，不凭聊天历史猜测。
5. 明确目标用户、触发场景、当前流程、期望结果、业务价值与可量化成功指标。
6. 划定本次范围和明确非目标；列出前后端、数据、运维和平台边界。
7. 收集正常、失败、边界、权限、并发、兼容、时间和历史数据场景。
8. 对每个未知项记录问题、决策人、截止点和未确认时的阻塞阶段。
9. 生成或更新 `00-request.md`、`01-clarification.md` 与 `status.yaml`。
10. 仅当关键歧义已消除且能够进入需求契约编写时，建议状态流转；不得自行批准 Gate。

## 技术约束

- uni-app 必须明确目标端：H5、微信小程序、App 或其他小程序，不能用“H5 可用”代表全端可用。
- 涉及登录、支付、上传、定位、扫码、分享、订阅消息或推送时，必须提出平台权限与真机验证问题。
- NestJS 请求需识别受影响模块、同步 API、定时任务、消费者和后台管理调用方。
- MySQL 变更需询问数据规模、历史数据、迁移窗口和恢复要求。
- Redis 变更需询问 Key 所有者、一致性、TTL、击穿/雪崩与失效行为。
- RabbitMQ 变更需询问生产者、消费者、投递语义、重复/乱序、重试和死信。

## 产物

- `00-request.md`：来源、类型、问题、目标、价值、范围、非目标、约束和风险。
- `01-clarification.md`：已确认事实、假设、问题、Owner、决定和阻塞项。
- `status.yaml`：正确的 Change ID、类型、目录名、当前状态和 Gate 状态。
- `source-baseline.json`：可版本化来源以及来源到正式需求的待建映射。
- 引用的知识 ID、相关 Change、代码或运行证据清单。

## 验证与证据

- 每个“当前行为”至少有代码、契约、日志、监控、复现或负责人确认之一支持。
- 每个假设有状态与 Owner；关键假设不得伪装成已确认事实。
- 检查目标是否描述业务结果，范围与非目标是否互斥且可判断。
- 检查所有外部依赖、旧客户端、后台任务和运营配置是否被纳入澄清。

## 停止与升级条件

- 目标用户、核心业务规则、数据口径或权限责任人无法确定。
- 请求与已批准 Change 冲突，或会扩大到未经授权的系统。
- 需要访问生产数据、密钥或第三方账户才能继续验证。
- 事故仍在扩大；切换为止损流程并保留现有事实。

## 禁止事项

- 不替用户编造需求、审批、上线日期、成功指标或合规结论。
- 不把技术方案当作业务目标，不在澄清阶段直接修改代码。
- 不用“按现有逻辑”“体验优化”等无法验证的表达结束澄清。
- 不把未读取的仓库事实写成确定结论。

## 完成定义

请求类型、目标、范围、非目标、关键场景、约束、风险和未决问题均已记录；关键问题有 Owner；历史知识已检索；下一步可以编写可测试需求契约，或明确记录为什么仍停留在 `clarifying`。
